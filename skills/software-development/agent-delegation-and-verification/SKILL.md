# Делегирование блоков работы субагентам и проверка их отчётов

Когда работу надо отдать ролям (правило проекта, большой объём, нужна независимая проверка), а
оплата идёт по токенам. Здесь — как формулировать задание, что проверять после возврата агента и как
построить приёмку, которая реально что-то проверяет.

## When to Use

- многоэтапная правка одного репозитория, которую владелец хочет видеть по блокам и с ценой;
- есть роли-исполнители (файлы контрактов в репозитории, например `.claude/agents/*.md`);
- нужно, чтобы результат агента не принимался на слово, а был перепроверен координатором.

**Don't use for:** механику без записи в файлы — её координатор делает сам (`execute_code`); любая запись
в файл проекта — Orca-воркер (`GLOBAL_RULES.md` §9).

Механизм — Orca-воркеры (скилл `orca-worker-routing`); «субагент» и «ребёнок» ниже значат Orca-воркер.
`delegate_task`, `claude -p`, `codex exec` и субагенты в сессии — не маршрут, пока владелец не назвал
их сам. Разведка, сводка, правка по спеке — Opus 5.5 medium (простая разведка — low); Sonnet не
используется; Luna только достаёт и сливает сырьё, не анализирует и не правит.

## Процедура

1. **Спланировать блоками и оценить в вызовах API.** Блок = замкнутый результат (файлы + проверки +
   отчёт), а не тема. По каждому блоку: роль-исполнитель, цена, что владелец увидит в результате.
   Перед каждым блоком — явный акцепт, если владелец платит за токены.
2. **Задание самодостаточно** (шаблон — `templates/subagent-brief.md`): текст контракта роли, точные
   указатели `файл:строка` на каждое место правки И на образец для подражания, запрет читать проект
   целиком, списки «твои файлы» / «не трогай», запрет коммита и деплоя, путь отчёта, требование
   своего прогона тестов. Указатели — главный рычаг цены: без них агент перечитывает базовый
   контекст и инструменты, и расход растёт в разы при том же результате.
3. **Один файл — один агент.** Параллелить можно только независимые файлы; в задании явно перечислить,
   что занято другими. Вести список находок каждого блока — они переносятся в следующий блок.
   Параллельная волна, чьи файлы ссылаются друг на друга (карта → предметы → монстры), получает
   **id-контракт в самой спеке**: все перекрёстные id фиксирует координатор, агенты используют их
   буквально и перечисляют в отчёте висящие ссылки на чужие, ещё не сданные файлы. Общую
   часть (источники, решения владельца, проверки, формат отчёта) держать одним файлом и приклеивать к
   заданию каждого.
   **Разведка и дизайн идут параллельно**, каждый в свой файл; как только разведка сдана —
   разослать дизайнеру сообщением её жёсткие ограничения (5–6 пунктов «чего нет в движке»), чтобы он
   переделал затронутое до сдачи, а не после.
4. **После возврата агента — своя проверка, до всех разговоров о результате:**
   - `git status --short`: изменены ровно ожидаемые файлы (плюс новые отчёты, плюс ничего из «не трогай»);
   - хеш ключевого файла до/после — агент не должен править его сверх задачи (например, при приёмке);
   - свой прогон тестов/сборки/линтера: числа из отчёта агента проверяются только своими глазами;
   - прогон **ровно командами приёмки из плана и в их условиях** (например, тесты при поднятом
     стеке `docker compose up`, а не на голых сервисах): агент гоняет удобный ему вариант, и его
     зелёный CI этого не заменяет — общие Redis/БД с живым сервисом ловят гонки, которых CI не видит;
   - grep на каждое заявленное заявление/находку.
5. **Приёмка отдельным агентом; режим «опровергнуть» — только по триггеру.** Триггеры (они же —
   `docs/studio/STUDIO.md` §4): (а) правка трогает общего владельца факта — состояние, деньги,
   сохранение и миграции данных, протокол/API; (б) починка бага — сначала воспроизвести, потом
   проверить фикс; (в) закрытие этапа или релиз — один проход на этап, не на каждую карточку.
   Без триггера — обычная приёмка «по спеке» с доказательствами: команда и её код выхода
   (`common.md`). Опровержение — не третий проход: второй проход приёмки переключается в этот режим.
   Бюджет: не больше пяти целей, выбранных по диффу и рискам (остатки удалённого кода, дрейф доков
   и переводов, тест, проходящий по случайности); искать за пределами списка запрещено. Находки —
   по формату с серьёзностью и адресатом; починка — не его дело. Блокируют только «критично» и
   «существенно»; «незначительно» — карточка `debt-`, новый круг доработки не открывает.
6. **Проба мутацией — только если в блоке добавлен или изменён тест.** Одна проба: приёмка вносит
   намеренную поломку в код, требует FAIL именно по этому месту, откатывает по хешу и снова
   получает зелёный прогон. Без нового теста пробу не делать.
7. **Закрытие блока:** коммит с сообщением, перечисляющим блок и решения, пуш, деплой, сверка
   результата по хешам, отчёт владельцу «факт против оценки» (см. скилл `agent-cost-monitoring`),
   и таблица находок с распределением по следующим блокам.

Партии сгенерированных изображений (воркер на картинку, приёмка владельцем через `clarify`, ловушки
промптов и проверки файлов) — `references/image-batch-acceptance.md`.

## Pitfalls

- **Перед первой задачей сверить, что рабочий worktree содержит то, о чём говорит владелец.**
  Привязанный worktree/фиче-ветка может отставать от активной ветки на сотни коммитов — упомянутых
  файлов в нём нет, а `CLAUDE.md` старый. Найти свежую ветку (`git worktree list`,
  `git log`), проверить `git merge-base --is-ancestor HEAD <ветка>` и сделать `merge --ff-only`
  до запуска агентов: иначе вся волна строится на устаревшей базе.
- **Перед вопросами владельцу — сверить исходные документы между собой.** Противоречие
  (одно и то же решение записано по-разному в библии и в требованиях) выносится одним из
  вопросов первого раунда; после ответа правится сама ошибочная строка, а не только задание
  агенту. Неотвеченный вопрос в пачке переспрашивать отдельно — ответ владельца может
  расширить задачу сверх предложенных вариантов.
- **Решения владельца по итогам дизайна записывать в три места одним коммитом до старта
  реализации**: в сам дизайн-документ (строка «решено» над вопросами), в журнал решений
  проекта и в roadmap; агенты реализации читают документ, а не переписку.
- **Замечание владельца «механика X слабая / не нравится» без делегирования решения — в
  документ вариантов, не в правку дизайна.** Спека дизайнеру: диагноз цифрами (вклад в
  силу эталонных сборок, сравнение с соседними слоями и референсом), 2–3 цельных
  варианта, рекомендация, готовые развилки «вопрос + 2–4 варианта, рекомендуемый
  первым»; файлы — только этот документ. Если идёт прогон баланса — дослать в него
  варианты как ось сравнения, чтобы владелец выбирал по цифрам. Просьба «реши сам» —
  наоборот, воркер закрывает развилки сам и пишет каждое решение со строкой «почему».
- **При написании описаний по данным требовать список «чего нет в источнике»**
  (заявленная сильная сторона без умения, пустое поле, расхождение названий с i18n) и
  запрет досочинять. Дальше разобрать список: приведение к уже принятым решениям и
  источнику истины — сразу отдельной карточкой; новые механики и контент — вопросом владельцу
  или в задачу воркера этой зоны.
- **Отчёт ребёнка — это его самоотчёт.** «Харнесс 707/707» и «файлы не тронуты» проверяются своими
  командами; расхождение — сразу правка задания, а не спор.
- **Ребёнок может выйти за список файлов** (трекер, конфиг, чужой отчёт) — ловить на `git status`, а не
  доверять обещанию из задания.
- **Без указателей `файл:строка` расход блока выше в разы** даже при правильном результате — это
  первый пункт, который надо срезать при снижении цены.
- **Не отдавать агенту одновременно правку кода и его же приёмку** — проверяющий ищет ошибки, а не
  отчитывается о том, что задание выполнено; совмещение гарантирует приёмку без находок.
- **Правки по замечаниям приёмки не терять:** список находок (что, где, серьёзность, адресат)
  переносится в следующий блок явными пунктами задания с указателями.
- **Не закрывать блок без собственного прогона проверок** — даже если агент приложил красивый вывод:
  проверка стоит одного запуска, а незамеченный регресс — дороже целого блока.
- **Пришедший отчёт сверять выборочно до сводки владельцу.** 2–3 ключевых факта (число, провал
  проверки, цитата исходника) перепроверить своей командой и назвать в ответе, что перепроверено.
- **Расхождение в числах с ребёнком — сначала пересчитать самому по источнику, потом возражать.**
  Ребёнок назвал счёт больше твоего, и прав оказался он: твой собственный однократный греп молча
  терял объекты, у которых поле записано скаляром вместо массива. Считай заново от исходных данных
  (разбор JSON/поиск по исходникам), а не от старой выдачи своего же скрипта.
- **Находка приёмки, которая противоречит утверждённому объёму, — это вопрос владельцу, а не
  правка.** Перечисляй два варианта с их ценой и рекомендацией: внедрение ограничения может стоить
  целого блока, а владелец может ответить «и так хорошо». Если объём смягчён, задача сжимается до
  исправления ложных утверждений в коде, тестах и доках — запрет писать не надо.
- **Развилку воркера «дешёвый обход сейчас / корневая правка с выходом в соседние зоны» по
  надёжности (сеть, протокол, синхронизация) решать в пользу корневой правки в текущей карточке**,
  если она укладывается в одну карточку: владелец предпочитает убрать слабое место сразу
  (потери пакетов у игроков), а не откладывать в идею. Карточку расширить (размер, разрешённые
  зоны, тесты на перехват/рестарт) и дослать воркеру. Развилку, где буквальное чтение карточки
  ломает баланс или чужие тесты, наоборот, решать вариантом без смены баланса и сообщать владельцу замером.
- **Отчёт приёмки — только входные данные.** Свой отчёт с найденной ложью (неверное движковое
  утверждение в комментарии или выводе) править надо; отчёт проверяющего — нет.
- **Спека фиксирует входы коммитом и не утверждает состояние дерева.** Писать «входы — по `<sha>`;
  если в дереве новее — остановись и спроси» и «статус X записать по файлу Y», а не «X не
  решено». Причина: владелец может коммитить в ту же ветку, пока агент работает, а агент
  перепишет устаревшее утверждение спеки в доки как факт.
  Обратная сторона: если карточку потом дополняли решениями (коммиты после `<sha>`), спека запуска
  прямо называет эти коммиты ожидаемыми входами. Иначе агент по правилу «входы новее» встанет на
  первом шаге.
- **Сохранность обязательных меток проверять счётом до/после**, а не чтением диффа:
  `git show <base>:<file> | grep -o '<метка>' | wc -l` против текущего файла по каждому файлу.
  При замене подразделов целиком потеря метки в диффе на сотни строк не видна глазом.
- **Параллельная волна по плану «сначала корень, потом пакеты» требует общего контракта в каждой
  спеке**, если корень делается одновременно с пакетами: версии рантайма и менеджера пакетов,
  формат модуля, форма `package.json`/`tsconfig` пакета, одна версия общих библиотек, кто коммитит
  общий lockfile (только владелец корня). Пакетным агентам — рецепт проверки без корня: временный
  корневой конфиг «не коммитить, удалить перед отчётом» и прогон в одноразовом контейнере. Без
  контракта ветки расходятся в базовых договорённостях, и мерж превращается в переписывание.
- **Находку одного живого агента для другого слать сразу**, пока тот работает (версия менеджера
  пакетов, имя скрипта, путь экспорта), а не чинить при мерже: сразу — одна строка в его работе,
  позже — правка чужой зоны координатором.
- **Сводить волну в отдельной интеграционной ветке**, не в master: мерж веток по порядку
  зависимостей, сверка заочных стыков (корневой скрипт ↔ скрипт пакета), затем ворота корневыми
  командами. Код, написанный без конфига форматтера корня, почти всегда падает на линтере —
  безопасный автофикс форматтера в интеграционном коммите, не возврат агентам. Master двигать
  `merge --ff-only` после зелёных ворот; красный шаг, зависящий от ещё не сделанной карточки,
  назвать владельцу.
  Даже если каждая ветка волны зелёная по отдельности — ворота на **слитом** дереве до push:
  ветка, добавившая обязательное поле в общий контракт, ломает ручные фикстуры соседней ветки.
  Такую однострочную стыковку чинит координатор сам и называет в отчёте.
- **Правку «только текст» (переписать описания, язык, подписи) проверять диффом чисел**, а не
  чтением: разобрать JSON до/после, собрать все числовые листья по путям и сравнить — допустимы
  только добавленные пути, ни одного изменённого или удалённого. Перезапись стиля на сотни
  строк прячет сдвинутое число от глаза.
- **Координатор в основном дереве коммитит свою правку по пути** (`git add <file>` →
  `git diff --cached --stat` → commit), не `git commit -am`: в дереве может лежать незакоммиченная
  правка прошлого шага или агента, и `-a` молча её заберёт. После коммита — `git show --stat` и
  grep ключевого слова своей правки в `git show`: попало чужое или нет своего — до push
  `git reset --soft HEAD~1` и заново. Правка файла скриптом: читать и писать с `newline=''`
  и искать якорь с тем же концом строки (`\r\n` в CRLF-файле), иначе якорь не найдётся
  или файл перевернётся целиком.
- **Параллельные агенты в одном дереве коммитят только свою папку:** `git commit -m ... -- <папка>`,
  при `index.lock` — пауза и повтор. Иначе `git commit -a` одного заберёт чужие
  незакоммиченные файлы.
- **Модель под роль выбирать по приёмке, а не по цене запуска.** После первого прогона роли
  на дешёвой модели запускать ревьюера (Opus medium): два прохода «по спеке» и
  «качество», баллы 1–5, вывод «что этой модели давать и что нет» и список правок с
  `файл:строка` для следующей карточки. Выводы перенести в профиль роли правилами.
  Синхронизацию доков (перенос решений, STATUS, CHANGELOG) владелец отдаёт Opus 5.5 medium,
  а не Luna: Luna правит только названные места и не видит противоречий в соседних строках.
- **Воркеры в фоне — всегда с подпиской на их итоги.** Координатор в Hermes gateway не видит
  `worker_done` и вопросы Orca-воркеров, пока сам не проверит inbox: без подписки сданная
  работа и стоящий на вопросе воркер ждут часами, и владелец замечает это первым. После
  запуска волны и после каждого пробуждения поднимать наблюдатель
  `terminal(background=true, notify=true)`: `python <skill>/scripts/watch_orca_inbox.py
  <handle координатора> 14400` (handle — из `orca terminal list`, вкладка Hermes). Перед
  первым запуском разгрести накопившееся (`check --terminal <h> --json`, затем `--ack <deliveryId>`
  в цикле, пока `deliveryId` не пуст) и сверить `check --all --json` с воркерами на экране.
  На `question` отвечать сразу (`orchestration reply` + дубль `terminal send`).
  **Ровно один наблюдатель:** перед запуском нового проверить процессы (`Get-CimInstance
  Win32_Process | ? CommandLine -like '*watch*'`; два python с одним временем старта — один наблюдатель
  через venv-лаунчер). Несколько наблюдателей берут одно непрочитанное сообщение до ack и
  будят координатора дублями. Дубль уже принятого итога — ack и одна строка владельцу.
- **Второй координатор на том же handle (вкладка TUI в Orca рядом с сессией в Telegram) —
  только наблюдатель.** Уведомления «You have N orchestration messages» приходят во все
  сессии этой вкладки, а `check` без флагов и `--ack` помечают батч прочитанным — наблюдатель
  ведущей сессии его уже не увидит, и итоги воркеров теряются. В неведущей сессии: `check --run
  <run> --peek` (фильтр `grep -v heartbeat`), ничего не ack'ать, не отвечать на `question`;
  решение владельца, принятое там, переслать ведущей сессии. Лишнюю вкладку посоветовать закрыть.
  Пришёл `worker_done`/`question`, а наблюдателя ведущей сессии нет (процесс `watch*.py`) —
  переслать владельцу сводку `hermes send` (что сделано, коммиты, ссылка, вопросы, `msg_id`)
  с фразой «скажите ведущей сессии принять `<msg_id>`», сообщение не ack'ать. Пропало из
  `--peek` — его забрала ведущая сессия, повторно не слать. Батч из одних heartbeat — ответ
  одной строкой. `status` с путями к картинкам тоже переслать владельцу (наблюдатель будит
  только на итоги, вопросы и эскалации): сначала `ls` путей, затем `hermes send -t
  telegram:<id> "MEDIA:<абсолютный путь>"` + подпись с `msg_id`; не ack'ать.
- **«Зависло в Telegram» — сначала жив ли gateway**: `hermes gateway status` и хвост
  `logs/gateway.log`. `gateway_state.json` со статусом `running` и мёртвым pid — процесс умер
  молча; `hermes gateway start` поднимает его, недоставленное доставляется само. `/handoff`
  сессии TUI в Telegram вреден, если там уже идёт своя сессия-координатор: он заменит её разговор.
- **Не освобождать (`worker-release`) воркера без его `worker_done`**, даже при массовой уборке
  «зависших»: отозванный dispatch отклоняет его итог (`capability is revoked`), и отчёт
  приходится доставать с экрана. Перед уборкой — `check --all --json` по `from_handle`.
- **Воркер на общей удалённой машине останавливает только свои процессы** (по PID или командной
  строке своей задачи) — писать это в спеке: «снять все фоновые powershell» обрывает чужие
  очереди (прогоны баланса).
- **Красную приёмку возвращать тому же живому агенту до его освобождения**: контекст уже
  загружен, починка — минуты, а новый агент перечитывает всё. Поэтому освобождать воркера
  только после собственной приёмки. В сообщении — упавшая команда, условие прогона, строка
  ошибки, путь лога и критерий «зелёно в обоих режимах N раз подряд».
- **Воркер сдал handoff (контекст ~200k) — продолжать свежим в том же worktree.** Записка коммитится в
  ветку (`tasks/open/<ветка>-handoff.md` или рядом с ассетами). Спека продолжателя: путь
  worktree + «ветка есть, новую не создавать», «записку прочитать ПЕРВОЙ, это спека», строка
  «сделано (коммиты)», новые решения, границы зон с параллельными воркерами, блок экономии
  контекста. Старого — ack, `worker-release`, `terminal close`. Старт свежего Claude-воркера
  ~70k (CLAUDE.md + профиль) — норма. Воркер, доходящий до 200k за ~час, — слишком широкая
  задача: следующую итерацию резать на две карточки.
- **Контент-трансформ через зоны двух параллельных веток (масштаб чисел ×N) — скриптом**,
  проверенным на копии (тест до/после), со списком масштабируемых и немасштабируемых полей
  (проценты/шансы — нет) и применением один раз после слияния обеих веток: правка в одной
  ветке даёт конфликты и оставляет новые числа соседа немасштабированными.
- **Инженерный вопрос воркера с разумной рекомендацией** (где лежит константа, как округлять,
  как развести зоны) — отвечать самому, владельцу — итог одной строкой. К владельцу —
  развилки дизайна: пачками `clarify` по 5, рекомендация первой, `[Б]` у чисел; пункт с
  ответом «не понимаю, детальнее» — отдельным вопросом с объяснением механики и примером в
  числах. Ответы сразу в файл решений проекта одним коммитом, затем свежий воркер по этому разделу.
- **Ресурсы хоста воркеров** — `references/host-resources.md` (лимит воркеров по RAM, Docker на
  несколько воркеров, перезапуск WSL без обрыва прогонов, деление прогонов между ПК).
- **Правки по замечаниям приёмки — отдельный блок той же роли-исполнителя, а не самодеятельность
  координатора.** В задании — цитата находки и `файл:строка`; в конце — свой прогон гейтов и хеши,
  как после любого блока.
