# Сведение веток разработки в master

Класс задач: «когда всё готово — слей ветки A и B в master, запушь и опиши, что тестировать».
Слить, разрешить, перепроверить, опубликовать тест-план. Проектные правила (CLAUDE.md: push в
master — только по договорённости) приоритетнее.

## Процедура

1. **Гейт готовности.** «После того как всё будет готово» = все воркеры приняты по диффу и
   закоммичены. До этого — только план слияния в ответе, без действий с master.
2. **Разведка refs:** `git fetch origin`; сравнить локальные и `origin/*` версии обеих веток и master;
   `git rev-list --count HEAD..<other>`; `git merge-base --is-ancestor origin/master HEAD`.
   `git worktree list` + `git -C <wt> status --short` по каждому worktree: незакоммиченное в
   чужом worktree в master не попадёт — не трогать, назвать в отчёте.
3. **Слияние в рабочей ветке, не в master:** `git merge --no-ff --no-commit <other>` → список конфликтов.
   - Конфликт в списках (каталоги деплоя и т.п.) — объединить обе стороны.
   - **Сгенерированные файлы не разрешать руками** — перегенерировать генератором после
     слияния исходников, даже если git слил их без конфликта: текстовое слияние двух
     артефактов не равно артефакту слитых данных. Затем `--check` генератора.
     Lockfile (две ветки добавили пакеты): `git checkout --ours pnpm-lock.yaml` → `pnpm install`
     (в контейнере проекта) → `pnpm install --frozen-lockfile && pnpm check` → коммит мержа.
   - Окончания строк: сверить с обеими сторонами (`git show <ref>:<file> | grep -c $'\r'`),
     писать байтами (Python `open(...,'rb')`), чтобы не перевернуть файл целиком.
4. **Перекрёстные смысловые зависимости.** Прочитать сообщения входящих коммитов и найти,
   где контент одной ветки описывает механику, которую поменяла другая (тексты, доки,
   книги про чужую механику) — сверить по коду, расхождение занести в тест-план. Git такие
   конфликты не видит.
5. **Полная валидация на слитом дереве до push** (пример из игрового мода: deploy → check_mods →
   lint_content → lua_harness → `gen_craft_costs --check` → `readme_smoke.js` → diff игровой копии).
6. **Каждый красный тест — доказать «был до нас», не верить отчёту:** временный detached
   worktree на базовом коммите каждой ветки (`git worktree add --detach <tmp> <ref>` → прогон →
   `git worktree remove --force <tmp>`; путь — нативный `C:/...`). Старый master без самого теста
   будет «зелёным» — это не доказательство; сравнивать с родителем первого своего коммита
   и с другой веткой.
7. **Тест-план в итоговом master** (если просили «что, как и чем тестировать»): файл
   `docs/qa/master-test-plan-<date>.md` + ссылка вверху roadmap. Состав — ниже. Коммит до push.
8. **Публикация fast-forward’ом:** если `origin/master` — предок HEAD, `git fetch . HEAD:master`
   (двигает master без checkout; работает, когда master не вытащен ни в одном worktree) →
   `git push origin master` → `git push origin HEAD` → `git fetch` и сверить `origin/master == HEAD`.
   Не fast-forward — остановиться и спросить, force не делать.

После мержа ветки воркера: `git worktree remove --force <wt>`; на Windows часто `Permission denied`
(каталог держит процесс вкладки воркера) — тогда `git worktree prune` + `git branch -D <ветка>`,
каталог удалить позже; мерж от этого не зависит.

**Массовая уборка worktree после приёмки волны** («всё слито — убери лишнее»):
1. Удалять только ветки с `git rev-list --count master..<b>` = 0 и только после зелёных ворот
   на master; ветку, где работа ещё идёт, оставить явно.
2. До удаления искать в каждом worktree **игнорируемые данные**, которых нет в git:
   `git -C <wt> status --short --ignored` без `node_modules|dist|__pycache__`. Сырые прогоны,
   логи, кэши переносить в основное дерево (путь тоже в `.gitignore`): после `rm -rf`
   их не вернуть.
3. Гасить процессы, которые держат файлы worktree (сервер страниц, монитор, запущенные из
   дерева воркера): иначе `mv`/`rm` дают `Permission denied`/`Device or resource busy`. Перезапустить
   их от основного дерева и проверить порт `curl` по tailnet-адресу.
4. Гасить docker compose стенды воркеров: `docker compose -p <COMPOSE_PROJECT_NAME> down` (у `down`
   нет флага `-q`). Стенды параллельных воркеров живут часами и съедают память хоста.
5. Итог сверить: `git worktree list`, `git branch`, пустые каталоги в корне папки worktree.

## Очистка старых веток (только по запросу владельца)

1. Обновить refs и инвентаризировать локальные и живые удалённые ветки: `git fetch --prune origin`,
   `git branch -avv`, `git ls-remote --symref origin HEAD 'refs/heads/*'`. Проверить фактическую
   default branch через `gh repo view <owner/repo> --json defaultBranchRef --jq '.defaultBranchRef.name'`;
   не выводить её из одного локального `origin/HEAD`.
2. Для каждой ветки проверить `git merge-base --is-ancestor <branch> <primary>` или
   `git rev-list --left-right --count <primary>...<branch>`: правая цифра — уникальные коммиты ветки.
   Если она ненулевая, ветку не удалять: сначала интегрировать эти коммиты и валидировать итог.
   Если все вершины уже предки primary, повторное слияние не нужно — содержимое уже в primary.
3. До удаления проверить `git worktree list`, чистоту рабочего дерева и открытые PR:
   `gh pr list --repo <owner/repo> --state open --limit 100 --json number,title,headRefName,baseRefName`.
   Не удалять ветку открытого PR; сначала явно решить судьбу PR. Не трогать default/primary branch.
4. Удалять только слитые ветки с явным разрешением владельца: удалённые —
   `git push origin --delete <branch>...`, локальные — `git branch -d <branch>` (не `-D`). Затем
   перепроверить удалённые refs через `gh api --paginate 'repos/<owner>/<repo>/branches?per_page=100'`
   или `git ls-remote --heads origin`, выполнить `git fetch --prune origin` и убедиться, что
   остались ожидаемые ветки и `HEAD == origin/<primary>`.
5. Если локальная `master` уже указывает на нужный финальный коммит, переключить рабочую копию
   командой `git switch master`, а не переименовывать поверх неё другой веткой через `git branch -M`;
   это сохраняет существующую ссылку и tracking-настройки. Удаление refs не удаляет файлы из дерева,
   а удаляет только имена веток; коммиты, достижимые из primary, остаются доступны.

## Состав тест-плана master

- Таблица «блок → что нового → состояние» и строка автопроверок с числами (и какой FAIL
  был до слияния).
- Подготовка одним списком: деплой, перезапуск, консоль, где лог.
- **Порядок прогона** таблицей «шаг → сейв (старый / новый мир) → набор → чек-лист и
  пункты»; миграцию старого сейва — первой, генерацию мира — на новом мире.
- Шаги не дублировать — ссылаться на существующие чек-листы; в плане — «что проверяем по
  сути», известные находки аудита и перекрёстные риски из шага 4.
- «Вторая очередь» — открытые проверки прошлых шагов: собрать скриптом из пунктов `[~]`
  roadmap с «Открыто: проверка в игре» (набор + чек-лист), не по памяти.
- «Что присылать»: ок / провал / не проверял; для провала — пункт, ожидалось/видно, лог, скриншот.
- Предметы — игровым именем (игра ищет по нему), id рядом.

## Отчёт пользователю

Хеш `origin/master`, какие коммиты вошли, разрешённые конфликты, числа проверок (с доказанным
старым FAIL), путь тест-плана, перекрёстные риски и что не сделано (перевод, баланс).
